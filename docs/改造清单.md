# mywork-home 改造清单

> 依据 2026-10-17 的代码审阅整理。当时前后端类型检查通过，单元测试 343 项通过、78 项集成测试默认跳过。
> 排序原则：先做改动小、收益直接的项，再做牵动面大的项。每个小节单独提交或单独开 PR。

## 第一阶段：可观测性与错误处理（预计 1～2 天）

### 1.1 开启服务端结构化日志

- [x] 在 `server/app.ts` 中启用 Fastify 自带的 pino 日志，配置 `redact` 路径，过滤 `authorization`、`apiKey`、`password` 等字段。
- [x] 每个请求生成请求 ID，并通过响应头回传。
- [x] 在 `setErrorHandler` 中，对用户仍然返回通用文案，服务端则记录错误类型、脱敏后的消息和调用栈。
- [x] 用日志实例替换 `main.ts` 里的 `console.*`。

完成标准：人为制造一次数据库断连和一次模型超时，都能在日志里找到对应的请求 ID 和原始错误类型，日志中没有明文密钥。

### 1.2 收掉吞错误的空 catch

- [x] 排查 `syncOrchestrator.ts`、`sessionScanner.ts`、`harness.ts` 中的 `catch {}` 和 `.catch(() => {})`。
- [x] 保留"不中断流程"的行为，但每处至少记录一条 `warn` 级别日志。只有清理类操作（关闭 harness、删除临时目录）允许保持静默。

完成标准：同步失败时，日志能定位到具体的来源和文件。

### 1.3 模型错误改用错误码

- [x] 给 `server/modelRouting.ts` 中的 `ModelConnectionError` 增加 `code` 字段，取值为 `TIMEOUT`、`CONNECTION`、`NO_API_KEY`、`VALIDATION`、`SHUTTING_DOWN`。
- [x] `harness.ts` 和 `nativeModel.ts` 抛错时带上 code。
- [x] `extractionBatcher.ts` 改为按 code 判断是否设置 `modelUnavailable`，删除正则 `/超时|校验|密钥|正在关闭/` 和 `/密钥|模型接入/`。
- [x] 补充单元测试：修改错误文案后，"模型不可用即停止整轮"的行为保持不变。

完成标准：`extractionBatcher` 中不再出现针对中文文案的正则。

## 第二阶段：重复代码收敛（预计 1 天）

### 2.1 统一生成凭据列表

- [ ] 新增 `server/secrets.ts`，导出 `runtimeSecrets(config)`，统一包含主模型密钥、数据库密码、`sourceSecrets` 和全部 `models[].apiKey`。
- [ ] 替换 `harness.ts`（4 处）、`syncOrchestrator.ts`（2 处）、`app.ts`、`mcpService.ts`、`settings.ts` 中手工拼装的列表。
- [ ] 补充测试：多模型配置下，非主模型的密钥在入库前和写入错误记录前都会被脱敏。

完成标准：执行 `grep "decodeURIComponent(new URL(config.DATABASE_URL).password)"` 只命中一处。

### 2.2 提取常量与工具函数

- [ ] 把同步咨询锁 `73921002` 提为 `SYNC_LOCK_ID` 常量（共 4 处）。
- [ ] 把多处出现的 `baseUrl.replace(/\/+$/, '')` 加账号的组合封装为 `zentaoIdentity(connection)`。

### 2.3 清理 `.gitignore`

- [ ] 删除开头的 Dynamics 365 AL 模板段（`.alpackages/`、`*.app`、`*.bclicense` 等）。
- [ ] 删除前确认没有依赖 `*.app` 这条规则的情况，它可能误伤 macOS 应用包。

## 第三阶段：数据库性能（预计 2～3 天）

风险最高，单独成一个 PR。先测量再动手，把改造前后的查询次数或执行计划写进 PR 说明。

### 3.1 补充索引

新增一个迁移版本，不修改历史迁移。

- [ ] 为 `contextMessages` 的查询条件加索引：`source_messages(source, root_session_id, occurred_at DESC) WHERE extracted AND valid`。
- [ ] 为 `invalidateEvidence` 在 `tasks.evidence` 上建 GIN 索引，或者新建 `task_evidence(task_id, message_id)` 关联表，以后者为优选。
- [ ] 用 `EXPLAIN ANALYZE` 对比改造前后的执行计划，结果记录到 PR 说明里。

### 3.2 扫描阶段批量预取

- [ ] 在 `CursorRepository` 中新增 `cursorsFor(paths[])` 和 `ignoredFor(paths[])`，各用一条 `WHERE path = ANY($1)` 查询。
- [ ] `sessionScanner.ts` 列出目录后先一次性预取游标和忽略状态，循环中直接查内存 Map。

完成标准：处理 1000 个未变化的文件时，数据库查询次数从约 2000 次降到个位数。

### 3.3 入库批量化

- [ ] `EvidenceRepository.ingest`：先用一条查询批量取出已有的 `body`、`body_revision`、`valid`，并加 `FOR UPDATE`。
- [ ] 消息插入改用 `INSERT ... SELECT FROM UNNEST(...)` 批量写入，会话 upsert 按 sessionKey 去重后批量写入。
- [ ] 保持现有的锁顺序（先消息、后事项）和编辑、撤回语义不变。
- [ ] 跑通 `npm run test:integration:local` 全部用例，重点覆盖 Gemini 快照撤回和原消息版本相关用例。

### 3.4 其他查询

- [ ] `resolveRoot` 改用 `WITH RECURSIVE` 一次查出完整父会话链。
- [ ] `periodTasks` 增加时间下界过滤，例如只取周期开始前 N 天以内仍然活跃的事项，并确认周月报的输出与改造前一致。

## 第四阶段：结构调整（预计 2～3 天）

### 4.1 前后端共享逻辑迁到 `shared/`

- [ ] 把 `src/domain/workbench.ts` 中后端用到的部分（`dateKey`、`requiresManualCompletion`、`Task` 类型等）和 `src/domain/periodicReport.ts` 的聚合逻辑迁到 `shared/`。
- [ ] `src/domain/` 改为从 `shared/` 重新导出，前端代码不需要改动。

完成标准：执行 `grep "from '../src/" server` 和 `grep "from '../../src/" server` 都没有结果。

### 4.2 拆分 `app.ts` 路由

- [ ] 按业务拆成 `server/routes/` 下的 `tasks.ts`、`reports.ts`、`settings.ts`、`zentao.ts`、`sync.ts`、`scheduled.ts`，每个文件都是一个 Fastify 插件。
- [ ] 来源校验、Content-Type 校验和错误处理保留在 `app.ts` 中统一注册。
- [ ] 可选：引入 `fastify-type-provider-zod`，用路由 schema 替代手写的 `parse`。

### 4.3 前端 `App.tsx` 状态收敛

- [ ] 把 `changingId`、`deletingId`、`pinningId`、`classifyingId` 和 `busy` ref 合并成一个 `pendingMutation: { id, kind } | null`。
- [ ] 用户操作被互斥拦截时给出可见提示，例如"正在保存其他事项"，不再静默忽略。
- [ ] 刷新时改为比较 `dataVersion` 来决定是否更新状态，不再用 `JSON.stringify` 比较整个快照。
- [ ] `SettingsDialog` 和 `ScheduledTasksDialog` 提到两个分支外层，只渲染一次。

## 第五阶段：运行性能（预计 2～4 天，需要先测量）

### 5.1 模型调用路径

- [ ] 先测量：统计一轮同步中 Harness 初始化耗时占模型调用总耗时的比例。
- [ ] 如果占比明显：凡是支持结构化输出的模型，默认走 `NativeModelClient`，Harness 只作兜底；或者在配置不变时复用 Harness 实例。
- [ ] 确认外部工具禁用、脱敏和引用消息 ID 校验仍然生效，并跑通 `npm run test:harness`。

### 5.2 Zcode 读取移出主线程

- [ ] 把 `ZcodeReader` 的 SQLite 查询放到 `worker_threads` 中执行，或者给单次读取的会话数加上限，分多轮完成。

完成标准：同步大型 Zcode 数据库期间，`/api/health` 的响应时间不受影响。

## 第六阶段：工程化（预计 1 天，可与其他阶段并行）

- [ ] 引入 Biome，或 ESLint 加 Prettier。设置最大行宽，先只在改动过的文件上强制执行，避免一次性产生巨大的格式化 diff。
- [ ] 新增 CI 流程，依次执行 `tsc -b`、`tsc -p tsconfig.server.json`、`npm test` 和 lint。
- [ ] 在文档中记录 `@deepseek-ai/dsh*` 的升级检查项：升级预发布版本前必须跑 `test:harness`。
- [ ] 可选：给写操作接口加一个本地访问令牌，防止本机其他进程在不带 `Origin` 头的情况下直接调用。

## 执行顺序

1. 先完成第一、二阶段。有日志才能对比后续改造前后的行为；凭据收敛到一处后，批量入库时不容易漏掉脱敏。
2. 第三阶段的 3.3 风险最高，独立成一个 PR，并用 `npm run test:integration:local` 验证。
3. 第三、五阶段先测量再动手，把改造前后的查询次数或耗时写进 PR 说明。
