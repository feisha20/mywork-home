# mywork-home（我的工作台）架构与工程改进方案

> **适用版本**：`v0.1.0`（Node.js >= 24 / React 19 / Fastify 5 / PostgreSQL 18 / DeepSeek Harness `0.2.0-rc.2`）
> **方案定位**：在不破坏现有数据契约、隐私脱敏边界与多模型高可用能力的前提下，解决单文件膨胀、高频轮询与磁盘扫描开销、历史日志检索缺失以及双状态源运维复杂性问题。

## 一、现状诊断：核心架构优势与待演进瓶颈

**[mywork-home](../README.md)** 已经构建了完整的「多源会话采集 → 模型抽取与证据校验 → 待办与日志归档 → 日报/周月报生成 → 本地 MCP 暴露」闭环，具备严格的凭证脱敏（`server/redact.ts`）、事务级游标推进与乐观锁并发控制。随着功能快速迭代，当前代码库在以下五个方面呈现出明显的演进瓶颈：

| 诊断维度 | 现状与具体表现 | 关联文件与体量参考 | 潜在风险或体验瓶颈 |
| :--- | :--- | :--- | :--- |
| **代码组织与耦合度** | 全局样式、数据库访问与同步编排集中在少数超大文件中；工作区同时保留构建产物目录 | `src/styles.css`（115 KB）、`server/store.ts`（编译后 38 KB）、`server/sync.ts`（编译后 33 KB） | 样式选择器易冲突，SQL 与业务逻辑交织增加改动回归风险，文件重命名易残留旧编译产物 |
| **同步扫描与模型效率** | 每轮同步全量遍历采集目录并 `stat` 文件；碎片化连续对话直接分页送入模型；Gemini 缺少原生协议 | `server/records.ts`（10 KB）、`server/harness.ts`（18 KB）、`server/modelRouting.ts`（3 KB） | 会话文件破千后空转 I/O 偏高；短促追问消耗额外 Token 与批次耗时；格式校验偶发触发二次修复 |
| **前端实时性与动效性能** | 依靠定时轮询获取同步进度与新待办；芯片外圈与流光按 10～20 FPS 更新；关闭页面后无系统通知 | `src/App.tsx`（20 KB）、`server/app.ts`（13 KB） | 状态感知存在最高 30 秒延迟，静默期产生冗余请求；JS 驱动高频动画占用主线程 CPU |
| **数据检索与报告安全** | `/api/records` 仅支持按起止日期分页；日报/周月报“重新整理”直接覆盖已保存正文 | `server/dailyReport.ts`（21 KB）、`server/periodicReport.ts`（4 KB） | 无法跨周期按关键词或项目检索历史事项；人工或 MCP 助手精修后的报告被重生成覆盖后无法一键找回 |
| **配置存储与容器运维** | 业务数据存 PostgreSQL，模型配置、路径与图标存 `.runtime/settings/workbench.json` | `server/settings.ts`（22 KB）、`compose.yaml`（3 KB） | 备份与恢复必须同时处理数据库和本地文件系统；Docker 新增宿主机采集目录需手工排查挂载配置 |

## 三、专项一：前后端巨型单文件模块化拆分方案

### 1. 前端样式体系重构（拆分 115 KB `src/styles.css`）

当前 `src/styles.css` 单文件超过 115 KB，混合了全局重置、设计变量、顶部状态栏、核心芯片与 SVG 采集连线、待办/日志列表、日历历史弹窗、日报/周月报弹窗以及设置中心。建议采用**「顶层 Token + 组件级 CSS Modules」**方案渐进拆分：

* **提取全局设计 Token（`src/styles/tokens.css`）**：
  * 统一收敛背景色、卡片边框、阴影、字体栈与圆角尺寸。
  * 语义化定义渠道与芯片状态色变量：`--status-connected`（绿色）、`--status-syncing`（橙色）、`--status-idle`（灰色）、`--status-warning`（琥珀色）。
* **按功能域拆分为独立样式模块**：
  * `src/components/WorkbenchCore.module.css`：负责中央智能芯片、引脚布局、采集渠道单排入口、`+N` 收纳胶囊及底部紧凑同步栏。
  * `src/components/TaskAndLogPanel.module.css`：负责左侧待办列表（置顶标记、完成按钮、禅道编号链接）与右侧工作日志卡片（个人事项开关、`AI` 标记、已整理/待整理徽标、证据折叠区）。
  * `src/components/ReportModals.module.css`：负责生成/查看日报弹窗、个人空间周月报三段式视图及日历日期选择弹窗。
  * `src/components/SettingsModal.module.css`：负责桌面侧边导航/小屏顶部导航、模型小卡片状态（首选/备用接管/正在调用）、路径核对卡片与 MCP 令牌管理列表。

### 2. 后端数据访问层与同步编排解耦（拆分 `store.ts` 与 `sync.ts`）

参照项目中已独立拆分的 `server/zentaoManagementStore.ts` 模式，将 `server/store.ts`（编译后 38 KB）和 `server/sync.ts`（编译后 33 KB）按领域边界拆分为高内聚子模块：

```text
server/
├── repositories/
│   ├── db.ts                   # 数据库连接池、事务包装辅助函数 (withTransaction) 与锁管理
│   ├── taskRepository.ts       # 待办与工作日志 CRUD、置顶排序、公私分类切换、旧缓存幂等导入
│   ├── cursorRepository.ts     # 各渠道字节游标、文件指纹缓存、连续失败黑名单与跳过计数
│   ├── evidenceRepository.ts   # 消息入库、正文版本比对、Gemini 快照撤回传播与按需证据查询
│   ├── reportRepository.ts     # 日报条目、整理标记、周月报持久化与乐观锁版本校验
│   └── syncRunRepository.ts    # 同步执行记录、状态统计与定时报告租约 (report_jobs)
└── sync/
    ├── syncOrchestrator.ts     # 全局同步锁、并发信号量 (WORKBENCH_SYNC_CONCURRENCY) 与渠道调度
    ├── sessionScanner.ts       # 本地目录扫描、兼容格式识别与增量消息提取入库
    ├── extractionBatcher.ts    # 未抽取消息分页 (500条/页)、6条上下文组装、短别名映射与还原
    └── zentaoSyncRunner.ts     # 禅道 Bug/任务拉取、移出列表详情补查与关闭/解决归档规则
```

### 3. 构建脚本清理加固

在 `package.json` 中补充构建前清理逻辑，防止文件拆分或重命名后在 `dist-server/` 中遗留旧 `.js` 文件：

```json
{
  "scripts": {
    "clean": "node -e \"fs.rmSync('dist', { recursive: true, force: true }); fs.rmSync('dist-server', { recursive: true, force: true });\"",
    "build": "npm run clean && npm run build:web && npm run build:server"
  }
}
```

## 四、专项二：实时通信（SSE）与前端动效合成层优化方案

### 1. 引入 Fastify SSE（Server-Sent Events）替代高频轮询

目前前端依赖定时轮询 `GET /api/workbench` 与 `GET /api/sync/:id` 来感知后台同步进度、模型切换状态以及禅道/计划任务生成的新待办（空闲时每 30 秒检查一次）。改为**「SSE 实时事件流 + 断线重连兜底」**后，前后端交互将更加轻量即时：

* **服务端新增 `GET /api/events` 接口（`server/app.ts`）**：
  * 维护本机活跃客户端响应流集合，发送标准 `text/event-stream` 响应头并每 25 秒发送 `: heartbeat\n\n` 保活。
  * 定义结构化事件类型：
    * `sync:progress`：携带当前正在扫描或抽取的渠道 ID、已处理批次、新增/更新数量及当前调用的模型别名。
    * `model:failover`：当首选模型超时或报错触发备用模型接管时立即推送，前端设置页与芯片状态即时更新。
    * `tasks:created`：禅道同步或计划任务调度器生成新待办时推送新事项摘要，前端立即触发「芯片 → 待办」流光动画并唤醒 Mac 系统通知。
    * `workbench:changed`：携带最新 `dataVersion`，通知多标签页按需增量刷新当日视图。
* **前端订阅与降级策略**：
  * 使用原生 `EventSource('/api/events')` 订阅事件；连接正常且空闲时暂停后台轮询；同步运行期间每 30 秒核对一次快照，防止完成事件丢失造成假采集中；`EventSource` 报错重连期间回退至低频轮询。

* **迁移兼容修复（2026-10-17）**：运行库曾存在版本 15 已登记、SSE 通知函数及触发器却缺失的状态，导致连接有心跳却没有变更通知。新增版本 17 幂等补齐通知对象，不删除旧迁移记录。已在运行库补齐 2 个函数、6 个触发器，并通过真实 SSE 接收验证；未重建或重启容器。前端运行中快照核对作为事件丢失兜底，需下次部署后生效。

### 2. SVG 芯片外圈与采集连线流光硬件加速

当前采集连线流光（空闲 16s / 工作 4s / 当前渠道橙色高亮 2s）与芯片圆角方框光弧在工作时以每秒 20 次（20 FPS）、空闲每秒 10 次更新。为避免主线程高频计算路径坐标或触发 React 重渲染，建议做如下改造：

* **纯 CSS `@keyframes` 驱动路径偏移**：
  * 利用 SVG 元素的 `pathLength="1000"` 属性将所有折线与圆角方框的长度归一化为 `1000`。
  * 通过 CSS `@keyframes chip-flow { from { stroke-dashoffset: 1000; } to { stroke-dashoffset: 0; } }` 将动画交由浏览器 GPU 合成器线程执行。
  * React 仅负责根据渠道状态设置内联 CSS 变量 `--flow-duration: 16s | 4s | 2s` 和 `--flow-color`，实现零 JS 定时器开销的丝滑变速。
* **尺寸测量节流**：保留现有的 `ResizeObserver` 测量引脚坐标逻辑，并使用 `requestAnimationFrame` 合并同一帧内的布局重算。

### 3. 可选扩展：基于本地 Web Push 的闭屏通知

针对“关闭工作台标签页后停止接收通知”的限制，可在现有 Service Worker 基础上引入 `web-push` 库：首次开启“待办通知”时生成本机 VAPID 密钥对并保存订阅端点；当 `server/scheduledTasks.ts` 或禅道同步产生新待办时，由服务端直接向本地浏览器推送通知，实现真正的后台常驻提醒。

## 五、专项三：会话增量扫描剪枝与 AI 抽取提效方案

### 1. 评估结论与实施边界（2026-10-17）

专项三可实施，但原始方案有三处需要调整：目录 `mtime` 无法证明已有文件未追加；时间接近无法证明消息属于同一事项；兼容接口不一定支持原生 JSON Schema。以下为修正后的实现，性能收益须通过样本测量，不承诺固定 Token 节省比例。

### 2. 目录项缓存与已完成文件指纹缓存

* `server/directoryCache.ts` 缓存目录项，以设备、inode、mtime、ctime 校验；仍逐层检查子目录，因此父目录时间不变也能发现深层目录变化。最多缓存 10,000 个目录，每小时强制重新列举；读取失败立即失效，遍历期间目录变化不缓存该次结果。
* **每轮仍检查候选文件指纹**，不按“超过 24 小时不活跃”跳过文件；旧会话追加、截断、替换均进入原有增量读取链路。该阶段减少重复 `readdir` 与数据库往返，不宣称消除全部文件 `stat`。
* `SessionScanner` 只缓存已成功读完或数据库游标确认读完的文件指纹，键隔离渠道、路径、采集器与字段映射；最多 10,000 项，每小时清空校准。半行、读取/入库失败、停止中断、忽略文件和未识别格式不会被标为成功。
* Codex、Claude、WorkBuddy、通用格式与 Gemini 文件采集接入目录缓存；Zcode 数据库采集保持现有方式。Gemini 仍每轮读取项目映射，不将映射正文缓存为目录状态。
* **`fs.watch` 暂缓**：其可靠性取决于挂载与事件环境。后续若引入，只能作为加速信号，不能作为跳过文件校验的唯一依据。

### 3. 紧凑对话块与证据边界

* 仅压缩相邻短消息的重复会话元数据，不合并正文或推断话题：同来源、同会话、同根会话、同项目，首尾间隔严格小于 3 分钟，单条不超过 400 字符、每块最多 8 条且总正文不超过 1,600 字符。
* 每条消息的角色、时间、正文和独立 `M`/`C` 别名完整保留；新增消息与历史上下文分开压缩。长消息、跨会话消息与不同项目不进入同一块。
* 保持原批次 ID、分页、30 条批次上限、事务提交与失败重试语义。本次优化输入体积，不承诺减少调用批次数；原始证据 ID 在本地还原并继续执行新增证据、未知证据、人工分类等校验。

### 4. 可选原生结构化输出与 Gemini 原生接入

* 模型配置新增 `structuredOutputs` 开关，设置页可启用；现有模型默认沿用 Harness，避免不支持新参数的兼容网关失效。开关针对事项抽取；其他汇总任务仍走现有调用方式。
* 启用后由 `server/nativeModel.ts` 发出非流式协议请求：Chat Completions 使用 `response_format.json_schema`，Responses 使用 `text.format`，Anthropic 使用强制且严格的 Tool Use。工具仅作为输出结构载体，本地不执行工具。
* 所有协议仍经过统一模型路由、超时预算与脱敏；输出无效最多修复一次；网络、HTTP 或协议不支持错误允许切换已启用的备用模型，不静默撤销约束。没有备用时按现有批次失败机制等待重试。
* 新增 `gemini_native` 协议，支持根地址或 `/v1beta`，调用 `/v1beta/models/{model}:generateContent`，API Key 使用请求头传递。事项抽取始终附带 `responseJsonSchema`；日报、周月报和旧事项摘要使用 JSON 模式并保留各自的本地校验。
* Gemini 2.5 Flash/Pro 使用 `thinkingBudget: 1024`，Gemini 3 系列使用 `thinkingLevel: low`，未知模型不附带推理参数。连接测试只验证原生连通性，不代表结构化输出能力验收。
* 原生请求共享整个纠错过程的超时预算，限制响应体为 2 MiB，关闭服务时中断请求；拒绝截断响应，忽略 Gemini 推理片段，上游错误正文不写入同步记录。

接口依据：[OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)、[Anthropic Structured Outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)、[Gemini generateContent 结构化输出](https://ai.google.dev/gemini-api/docs/generate-content/structured-output)、[Gemini 推理配置](https://ai.google.dev/gemini-api/docs/generate-content/thinking)。本次使用合成消息与本地协议桩验证，不向外部模型发送真实会话。

验证入口同时修正了已有测试运行器混用问题：`npm test` 使用 Vitest 执行业务测试，再使用 `node --test` 执行维护脚本测试，避免 Vitest 将 Node 原生测试误判为无套件。

## 六、专项四：工作日志全文检索与报告防误覆盖方案

### 1. 历史工作日志多维检索接口与索引设计

目前 `GET /api/records` 仅支持按 `startDate`、`endDate` 和 `onlyRecords` 分页读取。为满足跨周期回顾需求，建议扩展检索能力：

* **数据库索引扩展（`server/migrations.ts`）**：
  * 为任务与日志表的 `title`、`project_name`、`source`、`is_personal` 建立复合索引与 GIN 三元组索引（`pg_trgm`），支持毫秒级中文/英文模糊匹配。
* **查询参数扩展（`GET /api/records`）**：

| 新增查询参数 | 类型 | 行为说明 |
| :--- | :--- | :--- |
| `q` | `string`（可选） | 匹配事项简介（`title`）、项目名称或关联禅道编号 |
| `source` | `string`（可选） | 按来源渠道过滤（如 `codex`、`claude`、`zentao`、`manual` 等） |
| `project` | `string`（可选） | 按提取出的项目名称精确或前缀过滤 |
| `category` | `'work' \| 'personal' \| 'all'` | 按工作事项或个人事项筛选，默认 `'all'` |

* **前端交互**：在日历日志弹窗与工作日志顶部增加轻量搜索框与来源筛选胶囊，输入关键词时支持跨日期分页展示匹配结果，并高亮命中词。

### 2. 日报与周月报历史版本回溯（防覆盖保护）

当前用户在日报弹窗点击“重新整理”或在周月报点击重新生成时，新结果会直接替换已保存的报告（包括人工编辑或通过 MCP `save_report` 写入的精修内容）。建议引入轻量级历史快照表：

```sql
CREATE TABLE IF NOT EXISTS report_history (
  id BIGSERIAL PRIMARY KEY,
  report_type VARCHAR(20) NOT NULL,          -- 'daily' | 'weekly' | 'monthly'
  report_key VARCHAR(32) NOT NULL,           -- 如 '2026-10-16' | '2026-W42' | '2026-10'
  revision INTEGER NOT NULL,                 -- 对应的历史版本号
  content_json JSONB NOT NULL,               -- 日报结构化条目或周月报 Markdown 正文
  source_mode VARCHAR(20) NOT NULL,          -- 'auto' | 'append' | 'regenerate' | 'manual' | 'mcp'
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS idx_report_history_lookup
  ON report_history (report_type, report_key, revision DESC);
```

* **保留策略**：每次执行覆盖更新（`regenerate`、人工保存、分类变更触发重算）前，在同一个数据库事务内将旧版本写入 `report_history`，每个报告周期最多保留最近 5 个版本，超出部分自动按 `revision` 裁剪。
* **恢复接口**：新增 `POST /api/daily-reports/:day/restore` 与 `POST /api/periodic-reports/:type/:key/restore`（传入目标 `revision`），前端在“重新整理”完成后顶部显示“已更新，可撤回至上一版本”轻提示，彻底消除误操作顾虑。

## 七、专项五：配置状态源收敛与容器化部署体验升级

### 1. 收敛 `.runtime/settings` 至 PostgreSQL

当前业务数据存储在 PostgreSQL，而模型配置、API Key、渠道顺序与自定义上传的 Logo 保存在 `.runtime/settings/workbench.json`（见 `server/settings.ts`）。这种双状态源架构使得备份恢复脚本（`scripts/backup.sh`）必须同时停机打包数据库与本地目录。

* **统一入库存储**：
  * 新增 `workbench_settings` 表（单行 JSONB + `revision` 版本号）与 `channel_logos` 表（存储 `<= 256 KB` 的二进制图片 Buffer、MIME 类型与 `updated_at`）。
  * **密钥安全边界不降级**：模型 API Key 与禅道密码在入库前，使用环境变量 `WORKBENCH_MASTER_KEY`（首次 `setup.sh` 自动生成写入 `.env`）通过 Node.js 原生 `crypto` 模块执行 `AES-256-GCM` 加密存储；内存中仅在发起请求时解密，接口依然严格遵守“不回传明文”原则。
  * **平滑自动迁移**：服务启动执行数据库迁移时，若检测到 `workbench_settings` 表为空且存在 `.runtime/settings/workbench.json`，自动在事务内导入设置与图标并将原文件重命名为 `.migrated.bak`。

### 2. Docker 挂载路径自动诊断与配置生成

在 Docker Compose 部署下，容器只能读取已挂载的目录。当用户在设置页“路径设置”中手动输入一个新的 Mac 本机目录（如 `~/Documents/custom-agent-logs`）而容器尚未挂载时：

* 在 `POST /api/settings/check-paths` 返回 `unresolvedPaths` 的基础上，附带一段自动生成的 `compose.override.yaml` 挂载配置代码片段（例如 `- ~/Documents/custom-agent-logs:/records/custom/custom-agent-logs:ro`）。
* 前端在路径卡片提示处提供“一键复制挂载配置与重启命令”按钮，用户无需手动翻阅文档计算容器内部 `/records/...` 映射规则。

## 八、验证与回归测试清单

每一阶段改造完成后，均需通过以下三级验证流程确保零回归：

1. **单元测试与静态类型检查（`npm test` & `npm run build`）**：
   * 验证 Repository 拆分后的事务回滚、乐观锁 `409 Conflict`、公私分类变更对日报/周月报的级联影响。
   * 验证日志多维搜索参数（`q`、`source`、`project`、`category`）的 SQL 参数化绑定与边界分页。
   * 验证报告历史快照的写入、最多 5 个版本裁剪及按版本恢复逻辑。

   * 在临时隔离的 PostgreSQL 容器数据库中验证 `.runtime/settings/workbench.json` 自动迁移入库、AES-256-GCM 密钥加解密、SSE 事件推送与多实例并发同步锁。
